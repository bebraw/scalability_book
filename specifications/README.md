# Course Project Specifications

The course uses one common application contract and three phase-specific development setups:

1. [Project introduction](00_introduction.md) — the three projects, group and individual responsibilities, staged submissions, class access, and shared course guidelines.
2. [Common project specification](00_common_project.md) — required behavior, technical freedom, acceptance scenarios, shared runtime workload, transfer policy, evidence, and cross-team audit.
3. [Establish](01_establish.md) — implementation A with a large-model single agent.
4. [Challenge](02_challenge.md) — implementation B with a small-model single agent.
5. [Compare](03_compare.md) — implementation C with an agent fleet, analysis of its actual execution record, and the final comparison; importing the trace into C is optional.

The [course environment sheet](course_environment.md) defines the model, harness, access, budget, privacy, and fallback assignments for the current course run.
The [assessment rubric](grading.md) defines the project, participation, learning-diary, and self- and peer-assessment scoring.

Begin with the project introduction, then use the **What to do and submit** checklist at the top of the current phase brief alongside the common specification.
The common contract provides reusable [pressure-record](00_common_project.md#pressure-record-template) and [friction-audit](00_common_project.md#10-2-friction-report) templates for the existing evidence index and audit submission.
**Required**, **When applicable**, and **Optional** labels distinguish the matched fleet probe, arrival-controlled overload run, and additional model-assignment experiment.
Every phase includes an engineering session: rotating responsibilities for groups, or explicit solo passes and an instructor discussion for the [approved solo route](00_introduction.md#approved-solo-route).
All three phase briefs define the solo equivalents, while the common contract retains independent audits and the rubric preserves points and passing requirements.

## How chapter artifacts become submissions

The project or activity checkpoint in each main chapter supports the existing evidence bundle rather than creating another standalone file.
The common bundle and the current phase specification are the authoritative submission contract.
One clearly structured evidence document may satisfy several checkpoints when its headings make the required evidence easy to locate.

| Phase     | Chapter checkpoints                                                                                                                                                                                                                 | Where they are submitted                                                            |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Establish | Two bounded scalability claims; project harness and representative AI-use record; measurement and observation baseline                                                                                                              | Common bundle plus the Establish ownership card and large-model workflow reflection |
| Challenge | Architecture hypothesis and ownership card; both audits and one evidenced friction finding; primary pressure, bounded correctness or recovery case and Little's Law check                                                           | Common bundle plus A–B comparison and a link to the incident-transfer activity      |
| Compare   | Fleet plan, correction, actual-run debugging findings and supplied matched-trace analysis; three-way scaling comparison, implemented response, deployment evidence, and target design; final evidence matrix and decision narrative | Common bundle plus the Compare fleet evidence and final A-B-C package               |

Trace import, a student-run matched pair and additional pressure scenarios are optional; the required path supports full credit.

When a chapter suggests an optional lab or advanced appendix exercise, it becomes required only if the common or phase specification names it or the instructor announces it before the relevant phase begins.

The behavioral and assessment contracts are defined here.
Before each affected phase begins, the instructor must publish its supported assignments in the course environment sheet and the corresponding workflow details for that run.
