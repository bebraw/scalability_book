Isolation applies when concurrent work shares a transaction boundary.

The concurrent program and a conditional-write alternative

The simulation uses this read/check/unconditional-write program. Both callers read initial before either writes. The isolation choice changes the result for this program; read committed does not inherently require duplicate transitions. 

BEGIN
state = SELECT state FROM work_items WHERE id = :id
IF state = 'initial':
  UPDATE work_items SET state = 'active' WHERE id = :id
  INSERT work_started INTO activity_events
COMMIT

A different program can check the current state in the authoritative write. In PostgreSQL, a competing updater waits and rechecks its WHERE condition after the other update commits. Only the caller whose update returns a row appends an event, inside the same transaction: 

BEGIN
changed = UPDATE work_items SET state = 'active'
          WHERE id = :id AND state = 'initial' RETURNING id
IF changed has one row:
  INSERT work_started INTO activity_events
  COMMIT
ELSE:
  ROLLBACK
  reject transition

This is illustrative pseudocode, not executed SQL. Event-insert failure must roll back the state update. Check the chosen database's guarantees; see PostgreSQL read committed.
