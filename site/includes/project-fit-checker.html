Check whether your event idea can scale later

0/11 Start with the domain shape, then test scaling pressure.
Idea

Start with the domain language. A good idea has actors and objects that another group can understand later.

Pick a domain where meaningful things happen over time. Avoid a generic database exercise; the domain should have vocabulary another group can learn and analyze.
Name who creates events, views them, or depends on them. Distinct roles make authorization, workflow, and later team ownership easier to discuss.
Events should affect something: a ticket, session, device, order, workflow, node, or similar object. This gives the data model more structure than an event log alone.
Events

Define what changes in the system and how users will inspect that history.

Use concrete past-tense names. Three or more event types usually reveal whether the system has enough behavior for filtering, summaries, failures, and scaling pressure.
Describe how the domain changes over time. A state transition gives students something to validate, observe, benchmark, and later redesign.
Name how users read the event data. Views and summaries create realistic pressure around indexes, pagination, aggregation, freshness, and data retention.
Scaling pressure

Give the later Reconstruct phase something concrete to redesign.

Imagine the system becomes successful or receives a burst of automated events. Identify what grows first: writes, storage, dashboards, imports, logs, or review workload.
Scaling is more interesting when the same system serves many teams, locations, customers, classes, or projects with boundaries between their data.
Pick a query that sounds useful but may become costly: long date ranges, cross-tenant summaries, filtering by multiple fields, or rebuilding a timeline.
Risk and change

Name the operational and future-change pressures that make the system worth analyzing.

Choose a failure that affects event correctness: duplicate submissions, offline clients, retries, late delivery, partial writes, or inconsistent external systems.
Event data often describes behavior. Decide what should not be logged, how long raw events should survive, and what storage or compute could be wasted.
Name a likely requirement change. Good candidates involve new event types, revised states, different permissions, integrations, or changes to historical data interpretation.
